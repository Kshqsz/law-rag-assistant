# 智能法律问答辅助系统 - 数据库设计文档

本系统采取**双模型数据库架构**：关系型业务数据存储使用 **SQLite (通过 SQLAlchemy ORM 管理)**；法律文献与文档嵌入向量（Embeddings）知识存储使用 **ChromaDB 向量数据库**。

以下为核心关系型数据库（Relational Database）的表结构设计说明。

---

### 1. 用户表 (users)

| 字段名          | 类型        | 约束                 | 描述                               |
| --------------- | ----------- | -------------------- | ---------------------------------- |
| id              | Integer     | 主键，自增           | 用户的唯一标识 (系统分配)          |
| username        | String(50)  | 唯一，非空，普通索引 | 用户名（登录凭据）                 |
| hashed_password | String(255) | 非空                 | 密码哈希值（单向不可逆加密）       |
| is_active       | Boolean     | 默认 True            | 账户是否被激活可用                 |
| is_admin        | Boolean     | 默认 False           | 管理员核心标识（用于权限控制路由） |
| created_at      | DateTime    | 默认当前时间         | 账户创建注册时间                   |

**设计说明**：
该表用于存储本系统所有用户的核心身份信息和认证凭据。采用加盐哈希（`hashed_password`）确保用户隐私密码的安全。同时通过 `is_admin` 字段快速实现 RBAC 等级的权限划分，区分系统控制台后台管理员与前台使用问答的普通用户。

---

### 2. 对话记录表 (conversations)

| 字段名     | 类型        | 约束                 | 描述                               |
| ---------- | ----------- | -------------------- | ---------------------------------- |
| id         | Integer     | 主键，自增           | 对话主线 Session 的唯一标识        |
| user_id    | Integer     | 外键(users.id)，非空 | 该对话所属的用户 ID                |
| title      | String(200) | 默认 "新对话"        | 对话列表页显示的概要/标题          |
| created_at | DateTime    | 默认当前时间         | 对话树初始化创建的时间             |
| updated_at | DateTime    | ON UPDATE 当前时间   | 对话最后活跃的更新时间（自动维护） |

**设计说明**：
此表为每个用户切分出独立的多轮对话上下文作用域。每个用户可以创建大量的无状态并列对话模型（`user_id`），同时通过保留 `updated_at` 字段，方便前端系统实现以时间倒序的活跃度历史排序展示。

---

### 3. 消息明细表 (messages)

| 字段名          | 类型       | 约束                         | 描述                                         |
| --------------- | ---------- | ---------------------------- | -------------------------------------------- |
| id              | Integer    | 主键，自增                   | 消息流水的唯一标识                           |
| conversation_id | Integer    | 外键(conversations.id)，非空 | 级联绑定的会话 ID                            |
| role            | String(20) | 非空                         | 角色指代（"user" 用户 或 "assistant" 模型）  |
| content         | Text       | 非空                         | 发送和回复的具体 Markdown 文本内容           |
| law_context     | Text       | 允许为空                     | 回复时溯源引用的法律条文/内部知识库原文      |
| web_context     | Text       | 允许为空                     | 联网检索补充的鸭鸭搜(DuckDuckGo)网页参考来源 |
| created_at      | DateTime   | 默认当前时间                 | 当前问/答产生的物理时间戳                    |

**设计说明**：
该表存放所有实际的双边问答日志。特别在消息级别挂载拓展了 `law_context`（法律证据依据）和 `web_context`（网络引用源）两个长文本字段，这彻底固化了每次 RAG（检索增强）生成时使用的具体上下文，防止模型“幻觉”，同时便于平台审计人员事后回溯。

---

### 4. 上传文档表 (documents)

| 字段名            | 类型        | 约束                 | 描述                                                    |
| ----------------- | ----------- | -------------------- | ------------------------------------------------------- |
| id                | Integer     | 主键，自增           | 上传业务行为的唯一标识                                  |
| user_id           | Integer     | 外键(users.id)，非空 | 处理此合同文档的用户 ID                                 |
| filename          | String(255) | 非空                 | 服务端重命名的唯一安全防护防范静态文件名                |
| original_filename | String(255) | 非空                 | 客户端用户上传时的原始文档名称                          |
| file_path         | String(500) | 非空                 | 文档在服务器磁盘系统当中的相对或绝对路径                |
| file_size         | Integer     | 非空                 | 上传目标的文件兆字节大小 (Bytes 单位)                   |
| file_type         | String(50)  | 非空                 | MIME标准类型标志（如：`text/plain`或 PDF等）          |
| is_processed      | Boolean     | 默认 False           | **关键标志**: 当前文档是否已碎片化/向量化处理入库 |
| created_at        | DateTime    | 默认当前时间         | 资料完成云端上传的时间                                  |

**设计说明**：
用于专门处理用户个人的私有法律合同协议或证据录入库。专门引入 `is_processed` 设计处理队列解耦，由于 ChromaDB 做 Word/PDF 文档解析、Embedding转化非常耗时。前端可以依据这个字段反复轮询是否能够将此个人档案应用于用户的聊天检索。

---

### 5. 收藏夹表 (favorites)

| 字段名     | 类型     | 约束                    | 描述                                     |
| ---------- | -------- | ----------------------- | ---------------------------------------- |
| id         | Integer  | 主键，自增              | 用户收藏条目的唯一标识                   |
| user_id    | Integer  | 外键(users.id)，非空    | 触发保存动作的用户 ID                    |
| message_id | Integer  | 外键(messages.id)，可空 | 被收藏的源消息节点（允许级联失效时留空） |
| question   | Text     | 非空                    | 快照：收藏时的提问原文                   |
| answer     | Text     | 非空                    | 快照：收藏时的AI诊断解答原文             |
| created_at | DateTime | 默认当前时间            | 加入收藏夹的精确时间戳                   |

**设计说明**：
解决对话（Sessions）数据无用时被用户大面积清理但里面存在极高价值问答被连带抛弃的设计痛点。特意将 `question`和 `answer`做了全量文本冗余，作为冷固化数据独立保存，极大提升用户私藏备忘的自主性和数据稳定性。

---

### 6. 问题日志审计表 (question_logs)

| 字段名     | 类型       | 约束                     | 描述                                      |
| ---------- | ---------- | ------------------------ | ----------------------------------------- |
| id         | Integer    | 主键，自增               | 审计记录的唯一主键 ID                     |
| user_id    | Integer    | 外键(users.id)，允许为空 | 提出搜索访问的当事用户（支持缺失匿名）    |
| question   | Text       | 非空                     | 独立抽离出的所有脱敏搜索文本意图          |
| category   | String(50) | 允许为空                 | 依靠分类算法打上的核心标签（民法/刑法等） |
| created_at | DateTime   | 默认当前时间             | 会话流经管道的采集记录时间                |

**设计说明**：
这是一张专门预留给**管理员监控面板（Admin Dashboard）**做 ECharts 绘图提取统计用的审计脱敏表。将用户的原始输入内容与类型标记 (`category`) 集中管理，便于后端按日期 `group by` 和分析当前系统的“领域热搜”法律倾向。

---

### 7. Token 账单日志表 (token_usages)

| 字段名            | 类型        | 约束                         | 描述                                        |
| ----------------- | ----------- | ---------------------------- | ------------------------------------------- |
| id                | Integer     | 主键，自增                   | 账单凭证唯一记录 ID                         |
| user_id           | Integer     | 外键(users.id)，可空         | 触发产生开销的源头普通用户                  |
| conversation_id   | Integer     | 外键(conversations.id)，可空 | 扣除算力资源的对话上下文场景追踪标号        |
| prompt_tokens     | Integer     | 默认 0                       | 模型调用前的 Prompt/RAG拼凑上下文词元消耗量 |
| completion_tokens | Integer     | 默认 0                       | 模型吐出的作答词元数量损耗                  |
| total_tokens      | Integer     | 默认 0                       | 总共消费的运算长度合计                      |
| model_name        | String(100) | 允许为空                     | 本次应答提供算力的云端大模型名称 (例：Qwen) |
| created_at        | DateTime    | 默认当前时间                 | 核销记录记账操作时分秒                      |

**设计说明**：
专门设计负责成本监管及计费核心监控底座的独立表。在未来，无论是否要通过给用户发设“额度控制”（Rate Limits 等）或是测算平台的硬件调用及租约开支限制，本表作为细粒度的资源观测基点至关重要。

---

### 8. 用户主观反馈表 (feedbacks)

| 字段名     | 类型     | 约束                    | 描述                                             |
| ---------- | -------- | ----------------------- | ------------------------------------------------ |
| id         | Integer  | 主键，自增              | 评价收集记录的唯一标记 ID                        |
| user_id    | Integer  | 外键(users.id)，非空    | 在前端大拇指上点击动作的 ID 追踪源               |
| message_id | Integer  | 外键(messages.id)，非空 | 被用户标注具体判定的系统AI返回记录               |
| rating     | Integer  | 非空                    | `1`代表满意(👍推荐) / `-1`代表不合格(👎糟糕) |
| comment    | Text     | 允许为空                | 用户对糟糕解答自发提交的纠正文字版附注           |
| created_at | DateTime | 默认当前时间            | 评阅与打分产生的录入时间点                       |

**设计说明**：
由于生成式大模型在法律这个必须零容忍容错的环境中有局限性，此实体建立的核心目的是为了构建**人工反馈标注学习环 (HitL)**。管理员可将大量呈现评分为 `-1` 的差评问答从本表中筛出提取特征，以此改善 Langchain 下拉取文档片段的准度和修改过滤用的 Prompt Engineering。

---

### 9. 补充补充说明： 非结构化向量数据 (ChromaDB Vector DB)

> **存储地址位置**：项目源码目录中 `chroma_db/chroma.sqlite3` 及其同级段页式索引。

**设计说明**：
对于系统自带《民法典》、《刑法》等几十本电子书原文数据（`Law-Book`）和用户上传表中的 `documents` 源文件内容文本等高纬度的词义空间特征（1024 / 1536 维度），并非放在传统的关系型字段。而是由 Langchain 大模型提取意图切片之后存储在**ChromaDB 内核**进行向量召回计算。因此整个知识底座体现出 `关系逻辑链+语义意图链` 融合设计的高可用特征结构。
